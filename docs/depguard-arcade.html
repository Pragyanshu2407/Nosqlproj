▌THE BOSS: VULNERABLE DEPENDENCIES

Almost no modern application is written from scratch. A typical project pulls in dozens or hundreds of third-party packages from PyPI and npm, and those packages pull in more. When a flaw is found in any one of them, every project using the affected version is exposed, often without the developers knowing.

▌REAL INCIDENTS

LOG4SHELL · 2021

A critical flaw in the widely used Java logging library Log4j allowed remote code execution. Many teams did not know whether it was buried somewhere in their software.

EQUIFAX · 2017

A known flaw in the Apache Struts framework stayed unpatched and was exploited in a major data breach.

EVENT-STREAM · 2018

A popular npm package was taken over and shipped malicious code to the projects that depended on it.

▌THE PROBLEM

  • Developers rarely know which exact versions of packages they are using are vulnerable.
  • Checking each package by hand on advisory websites is slow and error-prone.
  • Advisories change constantly, and each has a different shape: several ID formats, severity ratings, version ranges and fixes.
  • Teams need to see what to fix first (severity) and what to upgrade to (fixed version).

▌WHY A DOCUMENT DATABASE WINS

  • Flexible structure. Advisories from OSV.dev differ: some have CVSS vectors, some do not; ranges, aliases and references vary. A document stores each one as it is, with no empty columns.
  • Embedding. A dependency can hold its list of vulnerabilities inside one document, so the results table needs one query instead of joins.
  • Maps to JSON. The OSV.dev API returns JSON, Flask works with Python dictionaries and React with JSON. No conversion layer is needed.
  • Powerful aggregation. The dashboard totals and severity chart are computed with MongoDB's $group and $unwind.
  • Indexing. Secondary and unique indexes support fast lookups and prevent duplicate advisories.
  • Simple for a student project. Easy local install, a readable query language and a clear fit with the data.

▌BONUS BOSS: WHY NOT SQL?

SQL databases such as MySQL or PostgreSQL are excellent tools, and DepGuard could be built on one. We did not choose it for these reasons:

  • The assignment is NoSQL. The activity asks us to pick a NoSQL type and design its data model, so a relational database would miss the learning goal.
  • Nested lists need extra tables. One advisory has lists of aliases, affected ranges, fixed versions and references. In SQL each list becomes its own table with joins. In MongoDB they are arrays inside one document.
  • Embedding avoids joins. A dependency stores its vulnerability summary inside itself, so the results table is one query. In SQL it would join dependencies, a link table and vulnerabilities.
  • Changing data shape. OSV advisories do not always have the same fields (CVSS vectors, ranges, aliases). SQL needs a fixed schema, NULL columns or migrations when a field is added. A document can simply omit or add a field.
  • JSON all the way. OSV.dev returns JSON, Flask passes dictionaries and React reads JSON. MongoDB stores it nearly as-is, with no object-to-table mapping.

Fair trade-off: SQL would give stricter data rules (foreign keys, fixed types) and our dashboard counts would also work there. We accept weaker enforcement and replace it with unique indexes and validation in the Flask code.

// dashboard chart: count findings per severity

  { $match:  { project_id: ObjectId("…") } },
  { $unwind: "$vulnerabilities" },
  { $group:  { _id: "$vulnerabilities.severity", count: { $sum: 1 } } }
